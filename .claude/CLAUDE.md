# CLAUDE.md

이 프로젝트(SMD News Monitor)에서 작업할 때 반드시 지켜야 할 개발 수준 기준입니다.

## 가장 중요한 원칙: 개발 수준

이 프로젝트는 **전문 개발자가 만드는 서비스가 아닙니다.**
일반인이 GPT나 Claude의 도움을 받아 본인이 만들고 싶은 서비스를 직접 만든 결과물입니다.

모든 코드는 반드시 다음 수준으로 작성하세요.

> **"1개월 정도 독학으로 AI나 개발을 공부한 사람(퇴근 후 하루 2~3시간 정도)이 GPT와 Claude의 도움을 받아 만든 서비스 수준"**

### 왜 이 수준을 지켜야 하나요?

- 서비스를 만든 사람이 직접 **발표**해야 합니다. 이해하지 못하는 구조나 기술이 들어가면 설명할 수 없습니다.
- 만든 사람이 **본인 서비스를 이해하고 직접 고칠 수 있어야** 합니다.
- 기능이 잘 돌아가는 것보다 **만든 사람이 이해할 수 있는 것**이 더 중요합니다.

## 이렇게 작성하세요

- 코드는 위에서 아래로 순서대로 읽으면 이해되도록 단순하게 작성합니다.
- 함수는 짧게, 하는 일은 하나만. 이름은 무엇을 하는지 바로 알 수 있게 짓습니다.
- 복잡한 부분에는 **쉬운 한국어 주석**으로 "이 코드가 무슨 일을 하는지" 적습니다.
- 이미 쓰고 있는 기술(FastAPI, SQLite, httpx, BeautifulSoup, 순수 HTML/CSS/JavaScript) 안에서 해결합니다.
- 오류 처리는 `try/except`로 잡아서 사용자에게 알기 쉬운 한국어 메시지를 보여주는 정도면 충분합니다.
- 설정값은 `app/config.json`이나 `.env`처럼 눈에 보이는 곳에 둡니다.
- 한 번에 큰 변경을 하지 말고, 요청받은 기능만 작게 추가합니다.

## 이런 것은 하지 마세요

다음은 독학 1개월 수준을 넘어서므로, 사용자가 **명시적으로 요청하지 않는 한** 사용하지 않습니다.

- 새 프레임워크·라이브러리 추가 (React, Vue, TypeScript, ORM(SQLAlchemy 등), Celery, Redis 등)
- 디자인 패턴·아키텍처 도입 (의존성 주입, 레이어드 아키텍처, 추상 클래스, 팩토리 패턴 등)
- 과도한 비동기·동시성 처리, 복잡한 락(lock)·트랜잭션 설계
- Docker, CI/CD, 클라우드 인프라 설정, 마이크로서비스 구조
- 지나친 성능 최적화, 캐싱 계층, 복잡한 정규표현식
- 여러 파일로 잘게 쪼개는 리팩터링, 공통 유틸리티 대량 생성
- 메타프로그래밍, 데코레이터 직접 정의, 제너레이터 체인 등 어려운 파이썬 문법
- 빌드 도구(webpack, vite 등)가 필요한 프론트엔드 구성

더 좋은 방법이 있더라도 위 수준을 넘는다면 쓰지 말고, 필요하면 "이런 방법도 있지만 지금 수준에서는 이렇게 했다"고 짧게 설명만 덧붙이세요.

## 기존 코드에 대해

- 현재 코드 중 일부는 이미 위 기준보다 복잡합니다. **요청 없이 전체를 다시 쓰지 마세요.**
- 새로 추가하거나 수정하는 부분은 위 기준을 따릅니다.
- 수정하는 김에 해당 부분을 더 쉽게 바꿀 수 있다면, 동작이 같은 범위에서 단순하게 바꿔도 됩니다.

## 작업 후 설명 방식

작업을 마치면 사용자가 발표 때 그대로 설명할 수 있도록 다음을 쉬운 말로 알려주세요.

1. 무엇을 바꿨는지 (기능 관점에서 한두 문장)
2. 어떤 파일의 어디를 바꿨는지
3. 어떻게 확인하면 되는지 (화면에서 무엇을 눌러 보면 되는지)

전문 용어는 꼭 필요할 때만 쓰고, 쓸 때는 괄호로 쉬운 설명을 붙입니다.

## 기능 문서 작성 (docs 폴더)

새 기능을 만들거나 기존 기능을 크게 바꿀 때마다 `docs/` 폴더에 **개발을 모르는 사람도 읽고 이해할 수 있는 설명 문서**를 함께 작성하세요. 사용자가 따로 요청하지 않아도 기능 작업의 마지막 단계로 항상 합니다.

### 왜 필요한가요?

- 발표를 듣는 사람, 함께 쓰는 동료, 나중의 나 자신이 코드를 열지 않고도 "이 기능이 뭘 하는지" 알 수 있어야 합니다.
- 기능이 쌓여도 서비스 전체를 설명할 수 있는 자료가 자연스럽게 모입니다.

### 파일 규칙

- 기능 하나에 파일 하나: `docs/기능이름.md` (예: `docs/AI요약.md`, `docs/CSV내보내기.md`)
- 이미 있는 기능을 고쳤다면 새 파일을 만들지 말고 해당 문서를 고칩니다.
- `docs/README.md`에 전체 기능 목록(문서 링크 + 한 줄 설명)을 두고, 문서를 추가할 때마다 한 줄씩 늘립니다.

### 문서에 들어갈 내용 (이 순서대로)

1. **한 줄 소개** — 이 기능이 무엇인지 한 문장으로
2. **왜 만들었나요** — 어떤 불편함을 해결하는지
3. **어떻게 쓰나요** — 화면에서 무엇을 누르면 무엇이 보이는지, 순서대로
4. **어떻게 동작하나요** — 뒤에서 일어나는 일을 쉬운 말로, 단계별로 (예: "기사를 저장할 때 → GPT에게 본문을 보내고 → 받은 요약을 카드에 보여줍니다")
5. **설정 방법** — 필요한 설정이 있으면 어디에 무엇을 넣는지 (없으면 "따로 설정할 것 없음")
6. **알아두면 좋은 점** — 한계, 비용, 실패했을 때 어떻게 되는지
7. **관련 파일** — 어떤 파일이 이 기능을 담당하는지 (개발자용 참고, 맨 마지막에 짧게)
8. **작성일** — 문서를 쓰거나 고친 날짜

### 쓰는 방식

- 개발을 전혀 모르는 사람이 읽는다고 생각하고 씁니다. 코드는 넣지 않습니다(설정값 예시만 예외).
- 전문 용어는 되도록 쓰지 말고, 꼭 써야 하면 괄호로 풀어 줍니다. (예: API(다른 프로그램에 요청을 보내는 창구))
- 문장은 짧게, 목록과 단계 번호를 적극적으로 씁니다.
- 작업 후 설명에서 "`docs/○○.md`에 정리했다"고 알려 주세요.

## 실행과 확인

```powershell
.\run.cmd                                                     # 서버 실행 (http://127.0.0.1:8000)
.\venv\Scripts\python.exe -m unittest discover -s tests -v    # 테스트 실행
```

- 주요 파일: `app/main.py`(화면·API 연결), `app/service.py`(수집·저장 흐름), `app/crawler.py`(기사 가져오기), `app/rules.py`(키워드 분류), `app/ai_summary.py`(GPT 요약), `app/db.py`(DB), `static/`(화면)
- `start.js`는 예전 Cloudflare 버전으로 참고용입니다. 수정하지 마세요.
